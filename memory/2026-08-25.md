## Hermes Agent sessions (source='hermes') added later same day

- **Three stores, three strategies**:
  1. `~/.hermes/sessions/session_*.json` (Windows + WSL): legacy transcripts, STOPPED receiving new sessions ~May 2026. Read via UNC with head/tail regex metadata cache keyed by (mtime,size) — never full-parse 1500 files per rebuild.
  2. WSL `~/.hermes/state.db` (SessionDB, 3GB+, LIVE — gateway writes here): NEVER read over 9P/UNC. Bridge script `hermes_state_bridge.py` (in repo) executed via `wsl -d <distro> -e python3 /mnt/c/...`; modes list/msgs/stats/raw; read-only URI.
  3. Sessions table has everything denormalized (tokens, message_count, title, cwd, cost) → listing needs no message join; correlated subqueries took 7.4s, plain indexed columns instant.
- **Gotchas**: `~/.hermes` in WSL home is a SYMLINK to hermes-cristalina-sandbox/home — //wsl.localhost does not follow it (probe real path). wsl.exe pipe output is UTF-8 but Python decodes cp1252 by default → pass encoding='utf-8' + errors='replace'. Transient wsl.exe failures return returncode≠0 with stdout None — treat as empty result. Cron runs flood recency → bridge caps 200/source via ROW_NUMBER window.
- state.db pseudo-path: `hermes-state://<session_id>`; uuids `hstate-<message_id>`; file sessions use `hermes-<stem>` / `hmsg-<idx>`.

## Hermes Bench + OpenCode sources added to dashboard

- **Hermes benchmark runs** (`source='hermes-bench'`): each eval run dir = one session.
  - Discovered via WSL homes glob `*/workspace/projects/*/results` (found `gpqa-ornith-eval` and `hetzner-mini-bench` on Debian). Override with `HERMES_BENCH_DIRS` env var (os.pathsep-separated).
  - Run detection: dir with `run_manifest.json` or `recovery_manifest.json`.
  - Progress reconciliation: `.watcher_state.json` can be STALE — take max(done) of watcher/`progress.json`, and if a report JSON has `score`, the run is completed (use report `num` as total).
  - Active recovery run: `full-run-1-seed42-truncation-recovery-60k` (retry_results.jsonl lines are compact: sample_index/correct/tokens/latency, no question content).
- **OpenCode sessions** (`source='opencode'`): current OpenCode (v1.18.x) stores everything in SQLite `~/.local/share/opencode/opencode.db` (tables session/message/part; ms epochs in `time_created`/`time_updated`; tokens cached per session row; part types: text/reasoning/tool/step-start/step-finish, tool output inside `state`).
  - LEGACY `storage/**/*.json` store (24 sessions, Nov–Dec 2025) integrated later same day: same part schema as DB (parts under `storage/part/<messageID>/prt_*.json`, NOT per-session); shared `_build_opencode_record`; pseudo-path `<storage>::<ses_id>`; DB wins on id collision.
  - OpenCode reader emits each message's events ATOMICALLY (batch extend) so a mid-message limit can't strand tool_results on the next poll; connection wrapped in try/finally.
  - Routing trick: `_path` is a pseudo-path `<db>::<ses_id>`; `read_events` must NOT `os.path.getsize()` before checking `_is_opencode_path` (WinError 123 otherwise). Same pattern for bench run dirs (isdir check).
- Cursor semantics bench: uuids `bench-config`, `bench-<i>-q/-a`, `bench-report`. Report event only appended when stream reached EOF (else it lands mid-pagination); `after=bench-report` → skip all lines.
